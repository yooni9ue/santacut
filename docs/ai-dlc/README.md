# 산타컷 AI-DLC

요구사항을 코드·검증·배포까지 이어가기 위한 산타컷의 경량 개발 규칙이다. AWS AI-DLC의 단계별 산출물과 추적 가능한 인계 방식을 참고하되, 이 저장소의 규모와 도구에 맞게 구성한다. 공식 AI-DLC 패키지나 별도 실행 엔진을 설치한 상태는 아니며, 에이전트가 `AGENTS.md`와 이 문서를 읽고 작업하는 방식이다.

## 시작하기

다음처럼 자연어로 요청하면 된다. 별도 슬래시 명령은 필요하지 않다.

> AI-DLC로 파일 업로드 화면을 구현해줘. 기획과 디자인부터 확인하고 테스트·PR까지 진행해줘.

에이전트는 기존 코드와 관련 문서를 먼저 읽고, 아래 순서로 필요한 단계를 선택한다.

1. 목표·범위·완료 기준과 기존 지시를 확인하고 프론트엔드·백엔드·영역 간 변경 중 범위를 정한다. 이미 알려진 정보는 다시 묻지 않는다.
2. [작업 크기](workflow.md#작업-크기에-따른-진행)를 정하고 필요한 산출물만 만든다.
3. 요구사항 → 사용자 흐름·설계 → 구현 → 검증의 연결을 유지한다.
4. 작업을 나누는 경우 [역할과 인계 규칙](roles.md)에 따라 파일 소유 범위와 입력·출력을 명시한다.
5. 실제 실행한 검증과 남은 제한을 정리한다. 커밋·푸시·PR·머지·배포는 사용자에게 허용받은 범위만 수행한다.

현재 진행 중인 작업에 "AI-DLC로 이어서 해줘"라고 하면 새 작업을 만들기보다 기존 목표·결정·코드 변경·미완료 검증을 먼저 복원한다. 중단 직전의 [인계 기록](../templates/handoff.md)이 있으면 다음 행동부터 이어간다.

## 저장 위치

- 공통 개발 흐름·PR 규칙·공통 템플릿: 루트 `docs/`.
- 새 프론트 기획·디자인·개발·운영 문서: `frontend/docs/`의 해당 분류.
- 백엔드 문서: `backend/docs/`의 해당 분류와 기존 지침.
- 여러 영역을 잇는 작업의 상태·의사결정·산출물 링크: 필요할 때 `docs/ai-dlc/work-items/YYYY-MM-DD-short-name.md`.

작업 기록은 기존 문서나 GitHub 이슈·PR에 이미 충분히 남아 있으면 중복 생성하지 않는다. 기록을 만들 때는 [작업 브리프](../templates/task-brief.md)를 복사하고 관련 산출물을 링크한다. 비밀값, 세션 토큰, 원본 대화 파일을 기록하지 않는다.

## 프론트엔드·백엔드 적용

| 범위 | 기준과 확인할 계약 | 검증 위치 |
| --- | --- | --- |
| 프론트엔드 | Next.js·pnpm·Tailwind CSS·TanStack Query·Axios. 화면 흐름·접근성·API 응답/오류 계약 | `frontend/`: 린트·타입·Vitest·Testing Library·Playwright |
| 백엔드 | Kotlin·Spring Boot·JDK 25. 도메인 규칙·트랜잭션·인증·API 문서와 해당 영역 지침 | `backend/`: Gradle `check bootJar`, 기존 리뷰·검증 규칙 |
| 영역 간 | [API 연동 가이드](../api/frontend-api-guide.md)와 실제 OpenAPI의 경로·필드·상태·쿠키·CSRF·SSE를 함께 확인 | 양쪽 단위 검사와 가능한 실제 연결 검사. 모의/실제 결과를 구분 |

백엔드는 AWS, 프론트는 Vercel에 배포한다. 실제 세부 설정은 해당 영역의 지침·운영서·코드를 우선 확인한다. 이 공통 흐름은 프론트와 백엔드 모두에 적용하되, 각 영역의 코드·리뷰 규칙을 대체하거나 다른 영역으로 확대하지 않는다.

단계 이름만 완료했다고 구현·테스트·운영 배포를 완료한 것으로 간주하지 않는다. 예시 데이터 화면, API 모의 테스트, 실제 백엔드 통합 검증, 운영 배포는 구분해서 보고한다.
