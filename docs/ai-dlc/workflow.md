# 진행 단계와 완료 기준

모든 작업에 문서를 여러 개 만드는 대신, 변경의 크기와 불확실성에 맞게 진행한다. 작은 수정에서도 목표와 검증 결과는 남기되 별도 산출물 파일을 강제하지 않는다.

## 작업 크기에 따른 진행

| 크기 | 예시 | 필요한 진행 |
| --- | --- | --- |
| 작은 변경 | 문구·색상·간단한 오류 수정 | 기존 규칙 확인 → 수정 → 적절한 확인 → 결과 보고. 작업 기록은 대화나 PR로 충분하다. |
| 기능 단위 | 업로드 화면, 랭킹 페이지, API 연결 | 목표·완료 기준 정리 → 사용자 흐름·계약 확인 → 계획·구현 → 오류·경계 검증 → PR 인계. 불확실한 결정은 기록한다. |
| 여러 영역 변경 | 업로드부터 분석·공유까지 연결, 배포 구조 변경 | 공통 작업 브리프와 영역별 산출물 링크 → 의존 관계가 있는 작업 단위 분리 → 구현·통합 검증 → 배포·복구 계획. 분담 시 책임자를 정한다. |

이미 승인된 기획과 결정은 재사용한다. 새 요구가 기존 목표를 보완하면 범위와 계획을 갱신하고 계속 진행한다. 기존 목표와 양립할 수 없는 새 지시가 오면 남은 작업을 명시하고 전환한다.

## 1. Inception — 무엇을 왜 만들지 정하기

| 항목 | 기준 |
| --- | --- |
| 입력 | 사용자 요청, 관련 기획·디자인·API 문서, 현재 코드와 작업 상태 |
| 수행 | 사용자 문제와 성공 조건 확인, 실제 구현과 계획 구분, 화면 흐름·상태·API 계약 확인, 미확정 항목의 영향 판단 |
| 산출물 | 짧은 작업 브리프. 필요하면 사용자 흐름·화면 설계·API 계약·작업 단위 계획을 해당 영역 문서에 기록 |
| 완료 기준 | 목표·포함/제외 범위·확인 가능한 완료 기준이 있고, 다음 작업을 바꾸는 필수 질문이 해결됐거나 안전한 가정으로 명시됨 |

사용자에게 묻는 것은 구현을 가로막는 필수 정보, 큰 비용·권한·되돌리기 어려운 결정에 한한다. 기존 문서·연결된 소스·코드에서 확인할 수 있는 내용은 먼저 조사한다. 합리적으로 되돌릴 수 있는 세부 선택은 가정을 적고 진행한다. 매 단계마다 새 승인을 요구하지 않는다.

디자인 변경은 정상 화면뿐 아니라 로딩·빈 상태·검증 오류·실패·재시도·모바일 접근성을 포함한다. API 연결은 경로·필드·상태 코드·인증·CSRF·페이지네이션·작업 상태를 현재 계약으로 확인한다.

## 2. Construction — 작은 단위로 구현하고 입증하기

| 항목 | 기준 |
| --- | --- |
| 입력 | 작업 브리프, 기존 코드, 확정된 설계·계약, 해당 경로의 작업 지침 |
| 수행 | 작업 단위와 의존 관계 선택, 구현, 변경에 맞는 검증, 관찰된 실패 수정, 독립 검토가 필요하면 담당자에게 인계 |
| 산출물 | 코드·필요한 테스트, 바뀐 결정·실행 계획, 검증 결과와 남은 제한 |
| 완료 기준 | 완료 기준에 해당하는 동작이 구현되고, 필요한 검사에 통과했거나 실행하지 못한 항목과 이유·영향이 명확함 |

계획은 실제 변경에 맞게 갱신한다. 기존 기능과 사용자 변경을 덮어쓰지 않는다. 공유 작업에서는 파일 소유 범위를 나누고, 공통 파일 수정과 Git staging·커밋은 한 명이 조정한다.

### 영역별 검증 기준

아래 명령은 기본 도구이며 작은 문구 수정마다 전부 반복하라는 뜻은 아니다. 변경의 영향과 이미 실행한 결과에 맞춰 필요한 검사를 선택한다.

| 변경 | 우선 검증 |
| --- | --- |
| 스타일·문구 | 해당 화면·모바일 폭·읽기 순서 확인, 필요한 린트·빌드 |
| 폼·상태·공통 로직 | 경계·오류·상태 변화의 Vitest/Testing Library 검사 |
| 사용자 흐름 | Playwright로 핵심 이동·입력·재시도·대화상자 확인 |
| API 연결 | Axios 계약·CSRF·세션·취소·오류 처리, 가능하면 실제 백엔드 통합 검증 |
| 배포 설정 | 워크플로 문법·빌드·환경 검증. 로컬 성공과 GitHub CI·실배포 결과를 구분 |

- 프론트는 `frontend/`에서 `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, 필요 시 `CI=true pnpm test:e2e`를 사용한다.
- 백엔드는 JDK 25 환경의 `backend/`에서 `bash ./gradlew --no-daemon check bootJar`를 사용한다. API·도메인·영속성·보안 등 바뀐 범위에 맞는 테스트와 `backend/CLAUDE.md`의 기존 리뷰·검증 규칙을 따른다.
- 영역 간 작업은 OpenAPI와 [API 연동 가이드](../api/frontend-api-guide.md)를 함께 확인한다. 경로·JSON·상태 코드 변경은 호출자와 서버를 함께 검증하고, 어느 쪽 산출물이 먼저 필요한지 계획에 표시한다.

실패나 새 변경이 없고 필요한 검증이 이미 끝났다면 같은 검사를 불필요하게 반복하지 않는다.

## 3. Operations — 검토 가능한 변경을 전달하고 운영 상태 확인하기

| 항목 | 기준 |
| --- | --- |
| 입력 | 검증된 변경, 실제 검사 결과, 환경·배포 영향, 사용자에게 허용된 Git·배포 범위 |
| 수행 | 관련 변경끼리 커밋·PR 분리, 현재 PR 규칙 적용, CI 결과 확인, 요청된 경우만 머지·배포 |
| 산출물 | PR 또는 작업 결과, 환경 설정·호환성·복구 방법, 필요 시 인계 기록 |
| 완료 기준 | 요청한 산출물이 전달되고 상태가 정확함. 배포가 범위에 포함되면 실제 성공·주소·상태 확인까지 수행하거나 구체적인 차단 원인을 보고함 |

CI/CD 구성 완료는 운영 배포 완료가 아니다. Vercel 프로젝트·환경 변수·비밀값이 준비되지 않았다면 구성만 완료된 것으로 적는다. 인프라 생성·비용이 드는 서비스 연결·운영 데이터 변경은 기존 사용자 승인과 실제 영향 범위를 확인한다. 머지 요청이 없는 PR은 자동 머지하지 않는다.

## 상태와 중단·재개

작업 기록이 필요할 때 다음 상태를 쓴다. 이는 문서상의 작업 상태이며 별도 자동 실행 시스템이 아니다.

| 상태 | 의미 |
| --- | --- |
| 준비 | 목표와 입력을 확인하는 중 |
| 진행 | 설계·구현·검증이 진행 중 |
| 대기 | 다른 작업·외부 실행 결과를 기다리는 중. 기다리는 조건과 그동안 가능한 일을 적음 |
| 차단 | 필수 입력·권한·외부 상태가 없어 다음 필수 작업을 할 수 없음. 필요한 조치를 적음 |
| 완료 | 작업의 완료 기준과 요청한 산출물을 충족함 |

중단 시 [인계 템플릿](../templates/handoff.md)에 현재 목표, 이미 끝난 내용, 변경 파일·브랜치, 검증, 다음 한 가지 행동을 남긴다. 재개 시 기록만 믿지 말고 Git 상태와 실제 파일·외부 실행 상태를 확인한다.

최종 보고는 **구현 결과 → 검증 → 제한·다음 행동** 순서로 작성한다. 미완료 작업이 있으면 완료했다고 표현하지 않는다.
