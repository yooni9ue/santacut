# 에이전트 역할과 인계 규칙

역할은 책임을 구분하기 위한 기준이다. 모든 작업에서 여섯 에이전트를 생성하거나 병렬 실행할 필요는 없다. 작은 작업은 한 에이전트가 역할을 순서대로 수행한다. 실제 분담은 사용자의 위임 요청, 적용되는 작업 지침, 사용 가능한 도구·슬롯과 작업의 독립성을 보고 결정한다.

## 역할

| 역할 | 책임 | 받아야 할 입력 | 전달할 결과 |
| --- | --- | --- | --- |
| Planner | 목표·범위·완료 기준, 우선순위·의존 관계 정리 | 사용자 요청, 기존 기획·코드·진행 상태 | 작업 브리프, 가정·결정, 필요한 작업 단위 |
| Designer | 화면·사용자 흐름·문구·상태·접근성 설계 | 사용자 문제, 브랜드 결정, 지원 범위·계약 | 화면별 행동과 상태, 반응형·접근성 기준, 구현에 필요한 결정 |
| Implementer | 담당 경로에서 계약과 설계에 맞게 코드 작성 | 브리프, 설계·계약, 경로별 지침 | 변경 코드, 필요한 테스트, 실제 동작과 제한 |
| Reviewer | 요구·회귀·유지보수 관점에서 독립 검토 | 최신 diff, 완료 기준, 실행 결과 | 근거 있는 문제와 파일 위치·영향·수정 제안. 문제 없으면 검토 범위를 명시 |
| Tester | 완료 기준을 관찰 가능한 검사로 확인 | 사용자 흐름, 경계·실패 조건, 실행 환경 | 실행 명령·결과, 실패 재현, 검증하지 못한 항목 |
| Release | 커밋·PR·CI·배포 상태를 정확하게 전달 | 실제 diff·검증·환경 영향, 사용자 승인 범위 | 관련 변경별 PR, CI·배포 상태, 필요한 설정·복구·인계 |

역할을 맡았다는 이유로 해당 권한이 자동 부여되지는 않는다. Reviewer는 원칙적으로 판정과 근거를 전달하고, 코드를 고치려면 변경 담당자와 범위를 다시 맞춘다. Release도 머지·배포 요청이 없으면 임의로 실행하지 않는다.

## 주 담당자의 책임

주 담당자는 전체 목표, 사용자와의 대화, 공유 파일·Git 변경, 최종 검증과 통합을 책임진다. 다른 에이전트에게 맡겨도 결과가 사용자 요구를 충족하는지 확인한다.

- 요구 변경·결정·실패 원인을 분담자에게 전달한다.
- 독립적인 읽기·설계·검토는 병렬로 할 수 있다. 같은 파일 편집과 의존 순서가 있는 변경은 순서를 정한다.
- 분담자에게 커밋·푸시·PR 권한까지 맡기는지 명시한다. 지정하지 않으면 결과와 변경 파일만 보고한다.
- 병렬 작업의 결과를 합친 뒤 실제 최신 코드로 필요한 통합 검증을 수행한다.
- 기존 영역별 규칙은 유지한다. 이 문서가 백엔드의 검토·검증 규칙을 대체하지 않는다.

## 분담 요청에 들어갈 내용

아래 항목을 짧게 전달한다. 전체 대화가 공유되더라도 작업 경계를 별도로 적는다.

1. 목표와 완료 기준.
2. 필요한 배경·확정된 결정·관련 문서.
3. 읽거나 수정해도 되는 경로와 건드리지 않을 경로.
4. 결과물과 검증 방법, 알려진 제약.
5. 다른 에이전트와의 의존 관계 및 인계 대상.
6. Git staging·커밋·푸시·PR·머지·배포 허용 여부.

예시:

> Designer 역할로 업로드 오류 화면을 설계해 주세요. 기존 화이트·먹색·빨강 테마를 유지하고, 빈 파일·20MB 초과·미지원 형식의 안내와 다음 행동을 정리해 주세요. `frontend/docs/design/`만 수정하고 실제 코드·공통 문서는 변경하지 마세요. 파일·결정·미확정 항목을 보고하고 커밋·푸시는 하지 마세요.

이 예시는 요청 형식이며 실제 파일 권한이나 위임을 생성하지 않는다.

## 인계와 검토 기준

인계는 [템플릿](../templates/handoff.md)을 사용하거나 같은 정보를 작업 이슈·PR에 남긴다. 파일 목록만 넘기지 말고 다음 담당자가 내릴 결정과 검증 결과를 함께 전달한다.

문제 보고에는 요구·계약·지침 또는 관찰된 동작의 근거를 적는다. 취향을 결함으로 단정하거나 실행하지 않은 테스트를 통과했다고 쓰지 않는다. 구현 변경이 필요한 경우 재현 조건, 기대·실제 결과, 영향, 수정 후보를 포함한다.
