# PR 작성 규칙

산타컷 저장소의 PR을 만들거나 수정할 때 이 문서와 [PR 템플릿](pull_request_template.md)을 함께 따른다. 사용자의 명시적인 지시가 우선한다.

## 브랜치와 커밋

- 변경은 목적을 알 수 있는 별도 브랜치에서 작업하고, PR의 기본 대상 브랜치는 `main`으로 한다.
- 커밋은 리뷰어가 따라 읽을 수 있도록 목적별로 나눈다. 서로 의존하는 설정과 코드는 함께 커밋한다.
- PR 생성 요청은 `main` 직접 푸시나 PR 머지를 포함하지 않는다. 사용자가 이를 명시적으로 요청한 경우에는 해당 지시를 따른다.

## 제목

`타입(범위): 한국어 요약` 형식을 쓴다. 타입은 `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore` 중 변경 목적에 맞게 고른다.

예: `ci(frontend): 모바일 웹 검증과 서버 배포 구성`

최종 변경 결과를 설명하는 구체적인 제목을 쓴다. 작업 중 범위가 달라지면 제목과 본문을 함께 갱신한다.

## 본문

아래 네 절을 사용한다. 검토자가 대화 내용을 몰라도 변경의 목적과 영향을 이해할 수 있게 쓴다.

### 개요

어떤 문제를 해결하며 사용자가 보게 될 동작이 어떻게 바뀌는지 1~2문장으로 설명한다. 필요한 경우 구체적인 변경 전후 예시를 든다.

### 변경 사항

리뷰에 필요한 주요 변경을 목적별로 병렬적인 글머리표로 정리한다. 각 항목은 한 가지 변경을 설명한다. 파일 목록을 그대로 나열하거나 대화 이력을 옮기지 않는다.

### 검증

실제로 실행한 명령, 실행 위치, 결과를 표로 적는다. 테스트 개수와 대상 브라우저 등 결과 판단에 필요한 정보가 있으면 포함한다.

| 실행 위치 | 명령 | 결과 |
| --- | --- | --- |
| `frontend/` | `pnpm test` | 실제 테스트 개수와 통과·실패 결과 |
| `frontend/` | `pnpm test:e2e` | 실제 브라우저별 결과 또는 미실행 이유 |

- 실행하지 못한 검증은 미실행 사실과 이유를 명시한다.
- 로컬 테스트 통과, GitHub Actions 통과, 운영 배포 완료를 구분한다.
- 모의 응답으로 검증한 결과를 실제 백엔드나 외부 서비스 통합 검증으로 표현하지 않는다.

### 영향·남은 작업

호환성, 환경 변수, 실행·배포 방법의 변경 중 실제 영향이 있는 내용과 확인된 한계만 짧게 적는다. 배포 설정이 있어도 서버·도메인·환경 설정이 끝나지 않았다면 완료된 것으로 쓰지 않는다. 남은 작업이 없으면 `없음`으로 표시한다.

## 작성 시 주의

- PR 본문과 첨부 로그에 토큰, 키, 비밀번호, 실제 환경 변수 값 등 비밀 정보를 넣지 않는다. 필요한 설정은 이름과 용도만 적는다.
- 본문은 현재 PR의 최종 구현을 기준으로 유지한다. 후속 커밋으로 범위가 바뀌면 검증 결과와 남은 작업도 갱신한다.
- `frontend/`와 `backend/`의 기존 작업 지침은 각 범위에서 적용한다. `backend/CLAUDE.md`는 백엔드 범위의 지침이며 프론트엔드 작업을 제한하는 규칙으로 확장하지 않는다.

## 제출 전 확인

- [ ] 검증 명령·결과가 실제 실행 내역과 일치하고, 미실행 검증과 한계를 명시했다.
- [ ] 배포에 필요한 서버·환경 설정이나 운영 확인이 남아 있다면 그 상태를 명시했다.
